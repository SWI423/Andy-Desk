# Andy 架构决策 · 通俗版

> 技术细节在 `docs/MEMORY_DESIGN.md`。这份文档只回答一个问题：**每个决定，你在用的时候会感觉到什么差别。**
> 原则：先用最少的零件跑通闭环，把"什么时候该换"写成明确条件，而不是凭感觉改。

---

## 决策 1：记忆检索先用"关键词对得上"，不逐条算语义向量

### 场景
你三天前说过"下周三软考"，今天问"我下周有什么事"。
- 用向量（语义相似）：能认出"软考"和"下周"的关系，即使你换了说法。
- 用关键词：要两句话里有相同的字，才容易召回。

### 最初想怎么做
每条消息都调一次 embedding 接口，把句子变成向量存起来，查询时算相似度取前 3 条。这是"标准做法"。

### 最后怎么做
`memory.search_events()` 对最近 300 条消息做**中文字符重合度打分**，超过 0.35 取前 3 条，并且排除刚刚已经发给模型的最近 6 轮。

### 为什么
| 维度 | 逐条 embedding | 字符重合 |
|---|---|---|
| 每条消息的额外请求 | 1 次 | 0 次 |
| 延迟 | 多 0.3~1 秒 | 几乎为 0 |
| 花费 | 按条计费 | 0 |
| 可解释性 | 分数不好解释 | 能说清"因为都出现了'软考'" |
| 换说法能不能召回 | 能 | 常常不能 |

现在你的数据量是几十条、问题多是"今天/明天要做什么"，关键词够用；为这个阶段付 embedding 的延迟和额度不划算。

### 你会感受到的差别
- 问"软考那个任务" → 能召回。
- 问"上次那个证的事"（没提"软考"）→ 可能召回不到。

### 什么时候该换
事件超过 2000 条，或你实测十个问题里有 1 个以上召回失败 → 接 `embedding-3` + 本地缓存 + 两路结果融合（RRF）。这是原方案第二阶段，代码入口已经留在 `search_events` 一个函数里。

## 决策 2：提醒用"每 30 秒看一眼表"，不是"每条提醒挂一个闹钟"

### 场景
你设了"每天 19:30 提醒弟弟写作业"。中途关掉程序、第二天再打开。

### 最初想怎么做
APScheduler 给每条提醒注册一个 job，到点触发。听起来最直接。

### 最后怎么做
APScheduler 只做一件事：每 30 秒检查一次 `reminders` 表，看 `next_fire_at` 有没有到期；到期的提醒触发一次，然后把下一次时间写回表里。所有状态只有一份——数据库。

### 为什么
如果"闹钟"和"数据库"各存一份状态，会出现两类事故：
1. 程序重启，内存里的闹钟没了，但表里还写着"已设置"→ 提醒永远不响。
2. 两边都恢复，同一条提醒响两次。

单事实来源的代价是精度：最快 30 秒才检查一次，所以 19:30:00 的提醒可能 19:30:25 才弹。

### 你会感受到的差别
- 关掉程序期间不会响；重新打开时，错过的提醒会合并成一条"错过提醒"，最多列 5 条，不刷屏。
- 到点误差在 30 秒内。
- 不会出现"重复弹两次"。

### 什么时候该换
需要关机也提醒 → 写 Windows 计划任务，开机自启；需要秒级精度 → 把心跳缩到 5 秒（代价是唤醒次数变多）。

## 决策 3：长期事实用"规则抓"，不每轮让模型总结

### 场景
你说"我叫 Wen，晚上十点后别提醒我学习"。
希望它记住：名字、这条偏好。但不希望它把"今天好烦"也当成长期事实存下来。

### 最初想怎么做
每轮对话后，再调一次模型："请从这段话里抽取值得长期记住的事实"。抽取质量最好。

### 最后怎么做
`memory.FACT_RULES` 里一组规则：出现"我叫/我的名字是"→ 记名字；"过敏"→ 记过敏；"考试/答辩/面试"→ 记学习锚点；"我不喜欢/我喜欢"→ 记偏好；等等。抓到后按"同类型 + 文本相似"去重。

### 为什么
- 成本：每轮多一次模型调用；一天聊 30 轮就是 30 次额外请求。
- 可控：规则抓什么、不抓什么，你能预期；模型抽取会自由发挥，还可能把情绪写进画像。
- 可测：规则能写单元测试，模型抽取只能抽样看。

### 你会感受到的差别
- "我叫 Wen""我对花生过敏""我十点后不想被提醒"→ 会被记住，下次对话自动带上。
- 你说"最近压力有点大"→ 不会写进长期画像（这是对的，情绪不是长期事实）。
- 你说"我每周二晚上固定打球"→ 目前规则里没有这条，可能漏记；可以让我加一条规则。

### 什么时候该换
发现规则漏记你真正在意的事 → 加一条 `FACT_RULES`（几行代码）；或加"对话结束后异步补抽"，不阻塞当轮。

## 决策 4：对话直接调 OpenAI 兼容接口，不用 LangChain

### 场景
你要的是流式输出（字一个个冒出来）+ 模型自己决定调哪个工具 + 工具报错不能把整轮对话弄崩。

### 最初（V1）怎么做
用 LangChain 的 `ChatOpenAI` + LCEL 链，工具循环交给框架。

### 最后（V2）怎么做
直接 `openai` SDK，`base_url` 指向智谱；工具循环自己写：
1. 流式请求，边收文字边拼工具调用参数；
2. 有工具调用就执行，把结果作为 `tool` 消息塞回去；
3. 再来一轮，最多 4 轮。

### 为什么
- 流式 + 工具调用的增量拼接，框架版本一变行为就变；自己写能定位到具体一行。
- 少一层依赖，出错误信息更直接（你看到的报错就是 API 的报错）。
- 你要拿这个项目讲"我怎么设计的"，自己写的循环比"框架帮我做的"更好讲。

### 你会感受到的差别
- 回复是流式的，不会等整段生成完才显示。
- 工具参数不合法、任务编号不存在，会变成一句人话，而不是整个对话报错。
- 升级模型只要改 `.env` 里的 `ZHIPU_CHAT_MODEL`。

### 代价
框架自带的多模型切换、回调、链编排要自己补。当前只有单模型、单轮工具循环，补的成本低。

## 决策 5：这一期不做 HTTP 服务，也不接 MCP

### 场景
你说"我有一个 FastAPI 项目，之后可以封装成 MCP 服务器"。这是明确的下一步，不是现在。

### 最初想怎么做
一开始就上 FastAPI + MCP，桌面端只当客户端，听起来架构更"正规"。

### 最后怎么做
桌面端直接调本地 Python 函数。工具层的契约（`TOOLS` schema + `TOOL_REGISTRY`）和"怎么调"分开：以后把实现函数换成 `requests.get(...)` 或 MCP 客户端调用，schema 和对话层都不用动。

### 为什么
- 现在只有一个用户、一台机器，多一层 HTTP 就多一层"端口没开/服务没起/序列化错"的故障点。
- 先证明"任务、提醒、记忆"这条链在本地跑通，再决定哪些能力值得服务化。
- 你的 FastAPI 项目本身也需要先明确"暴露哪些接口"，这要等 Andy 的工具清单稳定。

### 你会感受到的差别
- 现在：双击启动，不需要先开后端。
- 以后接 FastAPI：仍然双击启动，只是某些工具变成远程调用；失败时 Andy 会说"服务没连上"，而不是整个窗口打不开。

### 什么时候该换
需要手机端/多设备共享同一份任务数据，或需要把某个能力给别的程序用 → 先做 HTTP（S2），再做 MCP（S1）。

## 决策 6：单用户档案，先建档再谈多用户

### 场景
这是给 Wen 用的第一个版本。名字会影响称呼、画像归属和以后的数据隔离。

### 最后怎么做
`user_profile` 表存 `user_name=Wen`、`user_since`、`assistant_name=Andy`、`user_note=首位用户`，同时写一条语义事实 `name=Wen`，每轮对话注入。建档是幂等的：第二次启动不会覆盖。

### 为什么
- 现在就上账号体系，会把"登录、权限、迁移"的复杂度提前压到 MVP 上，收益为零。
- 但字段先按"有用户"设计（subject 字段、profile 表），以后加第二个用户不用重写记忆层。

### 你会感受到的差别
- 窗口左上角显示"服务对象：Wen"，开场白会叫你的名字。
- 改名只需 `python scripts/init_user.py --name 新名字`（不会覆盖已有资料，除非你要求）。

## 一句话总结

这六个决定都在做同一件事：**把"现在用不上的复杂度"换成"写清楚的升级条件"**。
你如果觉得哪个决定不符合你的使用习惯（比如希望提醒秒级、希望关程序也能响、希望每句话都语义检索），指出来，改一个函数就能换，不需要重做项目。
