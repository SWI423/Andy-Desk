## 0. 先约定几个词

不然后面每句都要停下来解释。

| 词 | 用大白话说 | 在这个项目里具体指什么 |
|---|---|---|
| **token** | 模型计费和"能看多长"的最小单位。中文大约 1 个字 1 个 token，英文大约 4 个字符 1 个 token | 我们用它衡量"每轮塞给模型的记忆有多重"，上限 2500（估算，不精确） |
| **prompt** | 发给模型的一整段输入，包含人设、规则、历史、你这句话 | `prompts.SYSTEM_PROMPT` + 每轮动态内容 |
| **前缀（prompt prefix）** | 每次请求里**完全相同**的开头部分 | 人设 + 处理范式，每轮一字不变 |
| **KV Cache** | 模型服务端把"相同前缀"的计算结果缓存下来，下次不用重算 | 前缀越稳定，响应越快、越省；这是"稳定前缀前置"的原因 |
| **embedding（向量）** | 把一句话变成一串数字，意思相近的句子数字也相近 | 本版默认使用：embedding-3，2048 维，存 `event_vectors` |
| **语义检索** | 用 embedding 找"意思相近"的历史 | 本版默认路径（向量侧） |
| **字面/关键词检索** | 两段文字里出现了相同的字或词，就算相关 | 本版作为降级与补充（关键词侧） |
| **RRF** | 一种把"关键词检索结果"和"向量检索结果"合并排序的算法 | 本版已用：两路各按名次贡献 `1/(60+名次)` |
| **schema（工具说明书）** | 告诉模型"有哪些工具、每个工具要什么参数"的结构化描述 | `core/tools.py` 的 `TOOLS` 列表 |
| **function calling** | 模型不直接回答，而是输出"我要调用某工具 + 参数"，由程序执行 | `brain` 里的工具循环 |
| **幂等** | 同样的操作做多次，结果和做一次一样 | 建档、建表都是幂等的 |
| **append-only** | 只追加、不修改旧记录 | `chat_events` 表 |
| **WAL** | SQLite 的一种日志模式，读写并发更好 | `core/db.py` 初始化时开启 |
| **心跳（heartbeat）** | 后台每隔固定时间醒一次，检查有没有要做的事 | 调度器每 30 秒检查提醒表 |

## 决策 0：命名与身份（Andy / Wen）

### 场景
你打开程序，希望它叫你名字，并且它自己知道"我叫 Andy，我在服务 Wen"。

### 怎么做
- 助手名：`config.APP_NAME = "Andy"`，窗口标题、聊天署名、CLI 提示都读这个常量；人设提示词第一句是"你是 Andy"。
- 用户名：`core/profile.py::ensure_first_user()` 首次启动写入 4 个字段 + 1 条语义事实：

| 键 | 值 | 作用 |
|---|---|---|
| `user_name` | Wen | 称呼、画像归属 |
| `user_since` | 2026-11-25 | 建档日期 |
| `assistant_name` | Andy | 助手名（与配置同步） |
| `user_note` | 首位用户 | 备注 |
| 语义事实 `name=Wen` | domain=general | 每轮注入给模型，模型因此知道"你是 Wen" |

### 关键函数

| 项 | 内容 |
|---|---|
| 归属 | `core/profile.py` |
| 函数 | `ensure_first_user(name="Wen") -> {"created": bool, "name": str}` |
| 行为 | 已有 `user_name` 就只补齐 `assistant_name`；没有才写全套 |
| 用错后果 | 如果你手动清空 `user_profile` 再启动，会重新建档；如果你用 `--name` 改成一个新名字，**不会**覆盖已有档案（这是有意的，避免误改） |
| 查看 | `python scripts/init_user.py --show` |
| 改名 | `python scripts/init_user.py --name 新名字`（当前实现只对未建档生效；要强制改，需要我加参数） |

### 你会感觉到的差别
- 窗口左上角：`服务对象：Wen`；开场白：`Wen，我在。`
- 问"我是谁"，它会答 Wen；问"你叫什么"，它会答 Andy。

## 决策 1：记忆检索用 embedding 语义，关键词留作降级

### 一句话
**找历史先算"意思像不像"（embedding 向量），再和"字对不对得上"（关键词）两路排名融合；向量接口不可用才退回纯关键词，对话不会因此中断。**

### 场景（两个真实会遇到的）

**场景 A**：11 月 22 日你说过"下周三软考，帮我记一下"。11 月 25 日你问"我下周有什么事？"
- 关键词：有"下周"字样，能召回。
- 向量：也能召回，还能把"软考"和"证/考试"放在相近位置。
- 两路都命中时，RRF 会给同一条更高的分。

**场景 B**：你说过"周三要交软件设计师的证"，今天问"我那个证的事怎么样了？"
- 关键词：这句话 9 个字里只有"证""的"两个字对得上 → 2/9≈0.22 < 0.35，**召回不到**。
- 向量：实测余弦中心化后 0.11，能排到第一（详见下面的实测表）。

所以这次不是"先用简单的"，而是**直接把语义检索做成默认路径**，关键词只做降级和补充。

### 上一版（已废弃）：字符重合度打分

做法：把你这句话切成单字集合，历史也切一遍，分数 = 交集 ÷ 你这句话的字数，≥0.35 才算。

废弃原因：场景 B 直接失效（0.22 被阈值丢掉）；而"今天""了""的"这种常见字又会把无关内容抬到 0.4 以上。这两个毛病是同一个原因——**字面重合不等于意思相关**。

### 现在怎么做：写入、查询两条路径

**写入路径（不阻塞对话）**

1. 你说一句话 → 先落 `chat_events`，本轮对话照常进行；
2. `brain` 每轮触发一次 `memory.kick_backfill()`，起一个后台守护线程；
3. 线程按 id **从旧到新**找"还没有向量"的事件，每批 16 条，调 embedding-3；
4. 拿到 2048 维向量 → 归一化成单位向量 → float32 存 `event_vectors`（`BLOB`）；
5. 每轮最多补 400 条（`EMBED_BACKFILL_MAX`），补不完下次继续；失败立刻停，不刷接口。

为什么不在写入时同步算：每条多一次网络往返，几句闲聊就会明显卡顿；后台补索引的代价只是"刚说的话暂时没有向量"，而刚说的话本来就在最近 12 条原文里，不靠向量召回。

**查询路径（每轮一次，约一次 embedding 调用）**

1. 取最近 1000 条向量，算这批向量的均值 `mean`；
2. 你这句话 → embedding-3 → 单位向量 `q`；
3. **中心化**：`q - mean` 再归一化；每条历史向量也减 `mean` 再归一化；
4. 用点积算相似度（等价于中心化余弦），按分数降序；
5. 排除最近 12 条（它们会原样进 prompt，重复注入浪费预算）；
6. 只保留 `≥ max(0.10, 最高分 - 0.06)` 的，最多 10 条（`EMBED_MIN_SCORE`、`EMBED_MARGIN`）；
7. 关键词侧照旧算一遍（阈值 0.35，最多 10 条）；
8. **RRF 融合**：每路按名次贡献 `1/(60+名次)`，同一个事件两路都出现就累加，取前 3；
9. 拼成 `- (日期) 内容前 80 字` 注入"可能相关的往事"。

**降级顺序**：查询向量失败（网络/额度）→ 只用关键词；库里还没有向量 → 只用关键词；两路都空 → 不注入。任何一步失败都不会让这一轮对话报错。

### 关键函数

| 函数 | 归属 | 参数 | 返回 | 用错后果 |
|---|---|---|---|---|
| `embed_texts(texts, model=None)` | `core/embedding.py` | 一批文本 | `list[np.ndarray]` 或 `None` | 一次传太多条可能超接口限制；失败返回 `None`，调用方不判空就会写进零向量 |
| `embed_query(text)` | 同上 | 一句话 | 单位向量或 `None` | 进程内缓存 64 条；改模型参数后旧缓存不会自动失效，重启即可 |
| `_store_vector(event_id, content)` | `core/memory.py` | 事件 id、原文 | `bool` | 原文为空会白算一次；写入用 `INSERT OR REPLACE`，重复不会产生两条 |
| `backfill_vectors(batch=16, limit=400)` | 同上 | 每批条数、本次上限 | `{"embedded","failed","remaining"}` | `limit` 设太大 → 后台线程长时间占接口；失败立刻停，不会无限重试 |
| `kick_backfill(limit)` | 同上 | 本次上限 | `bool`（是否新起线程） | 重复调用不会起第二个线程；线程是 daemon，关程序即结束，下次启动继续补 |
| `search_events(query_text, top_k=3, mode="auto", threshold=0.35, exclude_recent=12)` | 同上 | 问句、条数、模式（auto/keyword/vector）、关键词阈值、排除最近条数 | `list[dict]`（含 `score/via/vector_score/keyword_score`） | `top_k` 调大 → 噪声挤预算；`exclude_recent=0` → 最近对话被重复注入；`mode="keyword"` 只用于排查，不是默认 |
| `_load_vectors(model, limit=1000)` | 同上（内部） | 模型名、最多加载条数 | `(ids, 中心化矩阵, 均值)` | 缓存按"条数+最大 id"失效；若原地改写向量不增删，缓存不会刷新 |

### 实例演练（实测数据，不是示意）

用 8 条合成历史（只有用户发言，避免助手回声干扰），真实调用 embedding-3：

| 问句 | 关键词 top1 | 向量 top1 | 混合第一 |
|---|---|---|---|
| 那个证的事怎么样了 | 无 | 周三要交软件设计师的证…（0.11） | 证句（vector） |
| 我下周有什么要交的 | 下周要交课程设计文档（0.44） | 同一条（0.24） | 同一条（both） |
| 中午吃饭要注意什么 | 无 | 妈妈说周末回家吃饭（0.23） | 吃饭句；**第二条是"我对花生过敏"（0.19）** |
| 今天状态怎么样 | 无 | 今天好累，不想动（0.37） | 好累句（vector） |

两个要点：

1. 0.11、0.37 这类数字**只用于排序和过阈值**，不是"11% 像"。绝对大小取决于语料和模型，不要拿去和别的系统比。
2. "中午吃饭"的第一名是"回家吃饭"而不是"花生过敏"，但过敏那条排在第二，会一起进上下文——最终由模型判断该提醒你避开花生。检索负责"别漏"，判断负责"说准"。

### 为什么必须"减均值"（这一步不做，整个方案会失效）

embedding-3 的中文向量有一个很强的公共方向，任意两句话直接算余弦都在 0.5 上下，相关与无关分不开。实测三组：

| 问句 | 对比句 | 直接余弦 | 减均值后 |
|---|---|---|---|
| 那个证的事怎么样了 | 周三要交软件设计师的证 | 0.641 | 0.108 |
| 同上 | 我把软考冲刺记到学习里了 | 0.625 | 0.102 |
| 同上 | 今天好累，不想动（无关） | 0.512 | 0.005 |

减法之后，无关句掉到 0 附近，相关句还留在 0.10 以上，阈值才立得住。代价是**均值的估计依赖语料规模**：只有几条历史时均值很粗，历史多了会更稳，但分布也会变，所以阈值需要复核（见下一节）。

### 弱点与代价（如实列出）

1. **依赖网络和额度**：接口挂了就降级到关键词，场景 B 那种换说法又会漏。
2. **阈值是在小语料上标的**：0.10 来自 8~16 条合成数据，不是通用常数；正式库积累到几百条后应当复核。
3. **同题挤占**：前 3 条可能全是软考相关，没有做多样性去重（MMR 之类）。
4. **不看时间与重要性**：三个月前和昨天的权重一样；`importance` 字段还没参与打分。
5. **补索引有延迟**：老事件要等后台线程跑完才有向量；补之前只能靠关键词。
6. **有调用成本**：每条事件一次向量化（批量 16 条一次请求），每轮查询一次（同一句话有缓存）；具体单价以服务商计费为准。
7. **向量和原文绑定**：事件是被追加的、不改写，所以目前不需要"改一条重算一条"的逻辑；以后若支持编辑历史，必须补。

### 你会感觉到的差别

| 现在能做 | 现在仍做不好 |
|---|---|
| 换说法召回（"证的事""要交什么"） | 跨多轮的指代（"那个"指什么，仍靠最近 12 条原文让模型自己判断） |
| 概括式、口语化提问 | 精确按某个词查全部记录（可临时用 `mode="keyword"`） |
| 向量挂了照常对话（退回关键词） | 完全不联网的记忆检索 |

### 什么时候该调、该换

- **事件超过 2000 条，或你实测开始漏**：先跑 `python scripts/check_retrieval.py`，把漏的问句加进去，看分数再决定调 `EMBED_MIN_SCORE`，不要凭感觉改。
- **同题挤占明显**：在 `_rrf_merge` 之后加"同一话题最多 2 条"或 MMR 去重。
- **要更准**：加 rerank——先取 10 条，再用小模型或规则重排，而不是继续调阈值。
- **不建议现在上向量库**：1000×2048 的矩阵在本地点积是毫秒级，FAISS/Chroma 只会增加部署和运维成本；等单机内存真的放不下再说。

对话层、工具层、窗口层都不用改，因为大家只依赖 `search_events()` 的返回结构。

## 决策 2：提醒用"每 30 秒看一眼表"，不是每条挂一个闹钟

### 一句话
**提醒的"唯一真相"只存在数据库一张表里；后台每 30 秒看一眼，到点就响。**

### 决定（2026-11-26）
**保持心跳方案，不改成“每条挂一个闹钟”。** Wen 授权 Andy 决定。理由：单表不会出现两套状态，重启/补发逻辑已经被测试覆盖，当前提醒量（几十条）下开销可以忽略。已知代价（程序关着不响、误差 ≤30 秒）作为当前版本边界接受；将来要关机提醒，加 Windows 计划任务是独立增量，不影响这套结构。

### 场景（三个真实会遇到的）

**场景 A**：你设了"每天 19:30 提醒弟弟写作业"，19:00 关掉程序，20:00 再打开。
- 如果"闹钟"只存在内存里：关掉就没了，第二天也不会响，但界面上还显示"已设置"——最坏的一种错。
- 如果"闹钟"和数据库各存一份：重启后可能恢复两个闹钟，同一条提醒响两次。

**场景 B**：你设了"11 月 28 日 09:00 提醒我交材料"，28 日 08:50 打开程序。
- 心跳方案：09:00 后的第一次检查（最多 30 秒内）触发。

**场景 C**：你 28 日 10:30 才打开程序，提醒已经过了 1.5 小时。
- 心跳方案：启动时做一次"补发"，把错过的合并成一条通知，不逐条刷屏。

### 做法 A（最初想做的）：每条提醒注册一个定时任务

逐步流程：

1. 建提醒时，除了写数据库，还向调度器注册一个 job（到点执行）；
2. 到点，job 执行，弹提醒；
3. 程序重启，从数据库把 job 一条条恢复。

问题在两处：

- **两套状态**：数据库说"已启用，下次 19:30"，内存 job 说"我这儿没有"。谁对？很难判断，最后往往靠"启动时全部重建"擦屁股，但重建期间可能重复触发。
- **恢复逻辑复杂**：一次性、每日、每周、已停用、已过期，要分别处理；漏一种就出事故。

### 做法 B（实际做的）：心跳 + 单表

逐步流程（对应 `core/scheduler.py`）：

**建提醒时**（`create_reminder`）：
1. 校验规则格式（`parse_expr`）；
2. 算下一次触发时间（`compute_next`）；
3. 写一行 `reminders`：内容、规则类型、规则表达式、`next_fire_at`、`enabled=1`。

**心跳时**（`Scheduler._tick`，每 30 秒）：
1. 查 `enabled=1 AND next_fire_at <= 现在` 的提醒；
2. 对每一条：**先**算出下一次时间并写回表（`_advance`），**再**触发回调；
3. 回调把内容交给窗口 → 右下角浮层 + 写进对话流。

**启动时**（`Scheduler._catch_up`）：
1. 查所有 `next_fire_at` 已过的提醒；
2. 如果迟到超过 10 分钟（`MISS_GRACE_MINUTES`）：`missed_count` 加对应天数，并把内容收进"错过清单"；
3. 无论迟到多久，都把下一次时间推到未来（一次性提醒则停用）；
4. 如果有错过清单，合并成一条 `type=catch_up` 的通知。

**为什么"先推进时间再触发"**：如果触发时程序崩了，至少下次时间已经写好，不会造成"同一条每 30 秒重复弹"的死循环。代价是极端情况下可能漏一次，但不会刷屏。

### 关键函数

| 函数 | 归属 | 参数 | 返回 | 用错后果 |
|---|---|---|---|---|
| `parse_expr(rule_type, rule_expr)` | `core/scheduler.py` | `rule_type`: once/daily/weekly；`rule_expr`: 时间表达式 | `(True, None)` 或 `(False, 错误信息)` | 不校验就入库 → 心跳算不出下一次，提醒永远不响 |
| `compute_next(rule_type, rule_expr, after=None)` | 同上 | `after` 默认现在 | `datetime` 或 `None`（一次性且已过期） | 传入过去时间当 `after` → 每日提醒也会算到过去 |
| `create_reminder(content, rule_type, rule_expr, task_id=None)` | 同上 | 内容、规则、可选关联任务 | `{"ok","id","next_fire_at","text"}` 或 `{"ok": False,"error"}` | 内容为空/时间已过 → 返回失败，不会半写 |
| `Scheduler.start(catch_up=True)` | 同上（类方法） | 是否启动补发 | 无 | 重复 `start` 会重复起心跳（内部有 `started` 保护） |
| `Scheduler._tick()` | 同上（内部） | 无 | 无 | 不拿锁并发跑 → 同一条可能被两个线程同时推进 |
| `Scheduler._catch_up()` | 同上（内部） | 无 | 无 | 不补发 → 关程序期间错过的提醒永远消失 |
| `Scheduler.fire_now(id)` | 同上 | 提醒 id | 无 | 只用于界面"测试"，**不会**改 `next_fire_at`，所以不会影响真实排期 |

### 实例演练

**建提醒**：11 月 25 日 10:00，设"每天 19:30 提醒弟弟写作业"。
- `compute_next("daily","19:30")` → 今天 19:30；
- 表里：`next_fire_at=2026-11-25 19:30:00`，`enabled=1`。

**第一次触发**：19:30:00 之后的第一次心跳（假设 19:30:18）。
- 查到到期 → `_advance` 算出明天 19:30 → 写回 → 回调弹窗 → 对话流出现"⏰ 提醒 弟弟写作业"。

**关程序再开**：19:00 关，20:00 开。
- `_catch_up` 查到 `next_fire_at=19:30`，迟到 30 分钟 > 10 分钟 → `missed_count += 1` → 推进到明天 19:30 → 发一条"启动时发现错过的提醒：弟弟写作业"。

**迟到 5 分钟**（19:35 打开）：
- 迟到 ≤ 10 分钟 → 不记 `missed_count`，但会推进到明天并**补发一次**，文案里标"刚到点：弟弟写作业"。
- 提示：补发只发一条汇总，不会按错过次数逐条刷屏。

### 你会感觉到的差别

| 有 | 没有 |
|---|---|
| 关程序期间不响；重开时补一条汇总（含"错过"和"刚到点"两类） | 关机状态下的提醒（需要 Windows 计划任务） |
| 到点误差 ≤ 30 秒 | 秒级精度 |
| 不会重复弹两次 | 单次补发只覆盖启动那一刻，之后的新提醒仍靠心跳 |

### 代价
- 后台每 30 秒醒一次（很轻，但确实不是零）；
- 一次最多检查几十条提醒，量大时要看查询效率（有 `next_fire_at, enabled` 索引）。

### 什么时候该换，换哪里
- **要关机也提醒**：写一个 Windows 计划任务，开机自启程序；或在系统层做通知（不属于本项目的 Python 代码）。
- **要秒级精度**：`TICK_SECONDS` 从 30 改到 5；注意唤醒次数变 6 倍。
- **要调整补发口径**：现在迟到 ≤10 分钟标“刚到点”补发、超过 10 分钟记 `missed_count` 进“错过”；改 `MISS_GRACE_MINUTES` 即可移动这条分界线。

## 决策 3：长期事实有两条路——规则抓 + 模型主动记

### 一句话
**"我叫 Wen"这种明确的事实，模型会主动调工具记；"我过敏"这种关键词明显的，规则兜底自动抓。两条路都写进同一张表，并去重。**

### 场景

**场景 A**：你说"我叫 Wen，以后叫我 Wen 就行。"
- 规则命中"我叫" → 抓"Wen"；
- 模型也可能同时调 `memory_save`；
- 两条路都写 → 必须去重，否则画像里两条"名字"。

**场景 B**：你说"我对花生过敏，别推荐带花生的。"
- 规则命中"过敏" → 抓"花生"（取关键词后的第一段）；
- 下次你说"中午吃什么"，它应该能想到"避开花生"。

**场景 C**：你说"最近压力好大，什么都不想干。"
- 规则不命中任何长期事实 → 不写画像（正确：情绪不是长期事实）。

**场景 D**：你说"我每周二晚上固定打球。"
- 规则表里没有这条 → 规则漏；
- 模型如果判断这是长期习惯，会调 `memory_save` 记下来（这是模型主动路径的价值）。

### 两条路分别怎么跑

**路 1：规则自动抽（被动）**

`memory.extract_facts(text)` 在每轮用户输入后调用，规则表 `FACT_RULES` 共 8 条：

| predicate（事实类型） | domain | 触发关键词 | 抓什么 |
|---|---|---|---|
| `name` | general | 我叫 / 我的名字是 / 叫我 | 关键词之后、第一个标点之前的内容 |
| `allergy` | life | 过敏 | 同上 |
| `chronic` | life | 慢性病 / 老毛病 | 同上 |
| `exam_anchor` | study | 考试 / 答辩 / 面试 | 同上 |
| `work_anchor` | work | 截止 / deadline / 交付 / 汇报 | 同上 |
| `preference` | general | 我不喜欢 / 我喜欢 / 别对我 / 不要对我 | 同上 |
| `habit_study` | study | 每天…学 / 固定…复习 | 同上 |
| `habit_life` | life | 每天…睡 / 作息 | 同上 |

抓取规则有一个硬边界：**只取关键词后面、第一个标点之前的那段，长度 1~60 字**。所以：
- "我叫 Wen，晚上十点后别提醒我" → 抓"Wen"（到逗号停）；
- "我下周有考试，但还没复习" → 关键词"考试"后面紧跟逗号 → 抓到空串 → **不记**（这是漏抽，见附录 D）；
- "我对花生过敏" → 抓"花生"。

**路 2：模型主动记（主动）**

模型看到工具说明书里有 `memory_save(predicate, object, domain)`，在它判断"这是长期有效信息"时调用。人设提示词里写了两条约束：
- 只记长期有效的事实（称呼、习惯、偏好、长期安排、身体状况）；
- 一次性闲聊、当天情绪，不写长期记忆。

### 去重规则（两条路汇合的地方）

`memory.upsert_fact(predicate, obj, domain, confidence, source_event_id)`：

1. 精确相同 → 只更新 `updated_at`；
2. 文本相似度 > 0.9 → 合并（用新文本覆盖）；
3. 一个是另一个的子串，且长度差 ≤ 6 → 合并（比如"Wen"和"Wen 同学"）；
4. 都不满足 → 新增一条。

**用错后果**：如果去掉去重，你说五次"我叫 Wen"，画像里就有五条名字，每轮注入五遍，既浪费 token，也会让模型以为你有多个名字。

### 关键函数

| 函数 | 归属 | 参数 | 返回 | 用错后果 |
|---|---|---|---|---|
| `extract_facts(text, source_event_id=None)` | `core/memory.py` | 用户原话、可选来源事件 id | 写入结果列表（可能为空） | 对整段长文调用 → 只抓第一个标点前的内容；对每句都调 → 重复写入（靠去重兜住） |
| `upsert_fact(predicate, obj, domain="general", confidence=0.8, source_event_id=None)` | 同上 | 事实类型、内容、领域、置信度、来源 | `{"ok","action","id","fact"}` | `predicate` 乱写（如"info"）→ 画像无法按类型检索；`obj` 超过 60 字 → 注入时过长 |
| `get_facts(domain=None, limit=20)` | 同上 | 领域、条数 | `list[dict]` | `limit` 太大 → 每轮注入过长，被预算裁掉，等于没注入 |

### 实例演练（同一个名字，两条路都写）

- 规则先抓到 `name=Wen`，写入 id=1；
- 模型随后调 `memory_save(predicate="name", object="Wen")`；
- `upsert_fact` 命中"精确相同" → 只更新 `updated_at`，表里仍然只有 1 条；
- 下一轮注入 `【关于用户】- name: Wen`。

### 你会感觉到的差别

| 会记住 | 不会记住 |
|---|---|
| 名字、过敏、慢性病、明确说的偏好 | 当天情绪、随口一句"好累" |
| "每天 7 点背单词"这类关键词明显的习惯 | 规则表没覆盖、模型也没主动记的习惯（比如"每周二打球"） |

### 代价
- 规则会漏（关键词后接标点就抓不到）；
- 模型主动记会"多记"或"记错"，所以需要去重和人工可删（目前删除入口还没做，见附录 D）。

### 什么时候该换，换哪里
- **加规则**：`FACT_RULES` 加一行，几分钟；
- **提高抽取质量**：对话结束后异步调一次模型抽取（不阻塞当轮），写到同一个 `upsert_fact`；
- **给用户删除入口**：在窗口加"画像"页，列出 `semantic_facts`，支持删除。

## 决策 4：对话直接调接口，不用 LangChain

### 一句话
**每次对话就是"发一次流式请求 → 模型说要调工具就执行 → 把结果塞回去再问一次"，这个循环自己写，最多 4 轮。**

### 决定（2026-11-26）
**保持直连 SDK + 自写工具循环，不上 LangChain。** Wen 授权 Andy 决定。理由：当前是单模型、单用户、工具数量个位数，直连能精确插入时间拦截、假报喜核对、丢历史重试这些保障；框架会把这些关键控制点藏进抽象层。已知代价（最多 4 轮、无多智能体编排）当前任务形态用不到。触发升级的条件：出现跨 5 步以上的复杂任务、需要多模型分工或可观测链路时，再评估编排层。

### 场景

**场景 A**：你问"今天还有什么要紧的？"
希望：字一个个冒出来，而不是等 3 秒整段出现；模型自己决定去查任务，而不是你手动点按钮。

**场景 B**：你问"模电实验报告我做完了"。
希望：它先找到那条任务、改成完成，再回复你"已标记完成"，而不是嘴上说"好的"但数据库没动。

**场景 C**：模型给了个不存在的任务编号 123456。
希望：工具返回"没找到"，它换一种方式（按标题找）或老实说找不到，而不是整个对话报错。

### 做法 A（V1 用的）：LangChain

`ChatOpenAI` + LCEL 链 + 框架的工具循环。好处是"标准"，坏处是：
- 流式和工具调用的增量拼接由框架处理，出问题时你看到的是框架的抽象错误；
- 版本升级可能改变行为（同一个写法，两个版本表现不同）；
- 想在中途插入"时间硬拦截""把工具失败变成一句人话"，要改框架回调，不直观。

### 做法 B（现在用的）：openai SDK + 自己写的循环

逐步流程（对应 `brain.ask_baymax()`）：

1. **时间硬拦截**（调模型之前）：如果句子里有“提醒我/叫我/别忘了/定时”，但没有任何**钟点**（HH:MM、X点、中文数字点、半小时、一刻、整点），直接反问“几点提醒你？”，**不调模型**。只给“明天/下周”也算没给时间，避免模型自己编 09:00。
2. **取历史**：从 `chat_events` 取最近 12 条（`HISTORY_LIMIT * 2`），此时**还没写本轮输入**，避免重复。
3. **组装上下文**：`memory.build_context()` 产出"事实 / 今日状态 / 召回"三段，按优先级裁剪到 2500 token 以内。
4. **拼消息**，顺序固定：
   ```
   [system] 人设 + 处理范式（恒定，一字不变）
   [system] 当前时间 + 动态上下文（每轮变）
   [user/assistant...] 最近 12 条原文
   [user] 你这句话
   ```
   **为什么这个顺序**：恒定部分放最前，服务端能缓存前缀；动态部分靠后，不破坏缓存。
5. **第一次流式请求**：带着 `tools` 说明书和 `tool_choice="auto"`；边收边把文字通过回调吐给窗口，同时把工具名和参数碎片拼起来。
6. 如果**没有**工具调用 → 这段文字就是回答，结束。
7. 如果**有**工具调用：
   - 把模型这轮的"我要调工具"记成一条 assistant 消息；
   - 逐个执行 `tools.call_tool(name, args)`；
   - 每个结果作为一条 `tool` 消息塞回对话；
   - 回到第 5 步，最多 `MAX_TOOL_ROUNDS = 4` 轮。
7.1 **假报喜拦截**：本轮明确要求写入（建任务/更新/记事实/设提醒），回复却出现“已设置/已记下/我会每天叫你”这类说法，而本轮没有任何成功的写工具 → 丢掉多轮历史、只带当前这句重试；提醒意图锁了工具却零调用也直接重试。重试仍不调工具，就如实说“没写进系统”，不再骗用户。
8. **落库**：用户这句话、最终回答各写一条 `chat_events`。
9. **返回并广播事件**：`{"reply","tools_called","tool_results","context_meta","context_preview","error","cancelled"}`；若传了 `on_event`，同时发出 `text_delta/tool_start/tool_result/approval_request/done/error`。桌面与 CLI 只消费事件，不各自解析返回值。

### 关键函数

| 函数 | 归属 | 参数 | 返回 | 用错后果 |
|---|---|---|---|---|
| `ask_baymax(user_input, on_chunk=None, session_id="default", on_event=None, should_stop=None)` | `core/brain.py` | 用户输入、旧流式回调、会话 id、事件回调、停止判断 | 上述 dict | `on_event` 里做耗时操作 → 卡住流；`should_stop` 永远返回 True → 每轮都取消；`session_id` 乱传 → 历史分裂 |
| `needs_time_clarify(text)` | 同上 | 一句话 | `bool` | 关键词表加太宽（比如把"记得"也加进去）→ 正常对话被拦截反问 |
| `_stream_once(messages, on_chunk=None, tool_choice="auto", on_event=None, emit_delta=True, should_stop=None)` | 同上（内部） | 完整消息列表、回调、工具选择策略、事件回调、是否发文字增量、停止判断 | `(文本, [{"id","name","arguments"}])` | 不加 `tools` 参数 → 模型永远不会调工具，只会嘴上说；把 `tool_choice` 当绝对保证 → 服务端可能不执行，仍要靠“假报喜拦截”兜底 |
| `tools.call_tool(name, args)` | `core/tools.py` | 工具名、参数字典 | 统一 dict；失败也是 dict | 直接 `raise` → 一次工具失败打断整轮；不校验名字 → 未知工具 |
| `tasks.find_by_title(title, limit=5)` | `core/tasks.py` | 标题关键词 | 未完成任务的列表 | 匹配阈值太低 → 改错任务；当前有"精确 → 包含 → 相似度 0.45"三级，宁可返回多个让你确认，也不静默改错 |

### 实例演练（场景 B 的实际日志）

```
[tool] task_update {'title': '模电实验报告', 'status': 'done'} -> True
reply: 好的，模电实验报告已经标记为完成了。
```

- 模型没有编造 id，而是传了 `title`；
- `_tool_task_update` 用 `find_by_title` 找到唯一一条 → 用它的 id 更新；
- 如果找到两条（比如"模电实验报告"和"模电实验报告（补交）"），会返回 `ok=false` + `candidates`，让模型问你选哪个。

### 这个设计里两处需要如实说明

1. **工具调用的第一轮，模型如果先吐了文字**，用户会先看到这句，随后才看到第二轮正式回答。当前用的 `glm-4-flash` 在测试里基本不产生这种"前置文字"，但换模型后可能出现。
2. **4 轮上限**是防死循环，不是能力上限。超过 4 轮还在调工具，会回一句"我先按你说的办了几步，剩下的下一句继续"。复杂任务可能被截断，属于已知取舍。

### 你会感觉到的差别

| 有 | 没有 |
|---|---|
| 流式输出、工具真实执行、工具失败不崩 | 多步复杂任务的无限工具循环 |
| 模型名只改 `.env` 一行 | 多模型并行、链式编排（要自己加） |

### 什么时候该换，换哪里
- **换模型**：改 `ZHIPU_CHAT_MODEL`；如果新模型对 `tools` 支持不好，`_stream_once` 里要加降级（先纯文本回答）。
- **要更多轮**：`MAX_TOOL_ROUNDS` 调到 6，但要配"每轮耗时上限"，否则一次对话可能拖很久。
- **要流式工具参数更稳**：给 `_stream_once` 加"参数 JSON 校验失败就重试一次"。

## 决策 5：这一期不做 HTTP；MCP 后来只接了 stdio

> 2026-11-26 更新：MCP 已按**决策 8** 实现 stdio 客户端；远程 HTTP/SSE 与 FastAPI 仍未做。本节保留当时的取舍，避免"文档说没接、代码已经接了"。

### 一句话
**现在窗口直接调本地函数；外部能力走 stdio MCP；HTTP 服务仍未接。工具说明书和对话逻辑不动。**

### 场景

**场景 A（现在）**：你双击启动，不用先开任何后端服务。说"记一条任务"，窗口直接写本地 SQLite。

**场景 B（以后）**：你希望手机也能看同一份任务。这时任务数据必须放在一个服务里，桌面端只是客户端。

**场景 C（以后）**：你希望别的程序（比如另一个 Agent）也能用 Andy 的"建任务"能力。这时才需要 MCP。

### 最初想怎么做
一上来就 FastAPI + MCP：桌面端只当客户端，所有能力走 HTTP。

### 最后怎么做：把"说明书"和"执行"分开

`core/tools.py` 里有两样东西：

1. `TOOLS`：给模型看的 schema（工具名、描述、参数类型、哪些必填）；
2. `TOOL_REGISTRY`：给程序用的映射（工具名 → 真正的 Python 函数）。

`brain` 只认识这两样，不认识"函数是本地还是远程"。所以：

- 现在：`_tool_task_create` 里直接 `tasks.create_task(...)`；
- 接 FastAPI 后：`_tool_task_create` 里改成 `requests.post("http://127.0.0.1:8000/tasks", json=...)`，schema 不动；
- 接 MCP 后：改成调用 MCP client 的 `call_tool("task_create", args)`，schema 不动。

### 为什么现在不做

| 现在做 HTTP | 现在的实际情况 |
|---|---|
| 多一个进程要启动、要监督 | 双击就能用 |
| 多一类故障：端口占用、服务没起、序列化错 | 故障只在本地函数里 |
| 要定义接口契约（路径、鉴权、错误码） | 接口契约还没稳定（工具清单还在长） |
| 收益：多设备共享 | 现在只有一个用户、一台电脑 |

### 你会感觉到的差别
- 现在：启动快，断网也能记任务、看板、提醒（只有对话需要网络）。
- 以后：仍然双击启动；只是部分工具变远程，失败时 Andy 会说"服务没连上"，窗口不会打不开。

### 什么时候该换，换哪里
1. 先定接口契约：你的 FastAPI 项目暴露哪些路径、用什么鉴权、错误格式；
2. 写一层 `core/remote.py`，把 `TOOL_REGISTRY` 里的函数替换成 HTTP 调用；
3. 保留本地实现作为降级（服务连不上时退回本地）；
4. 之后再考虑 MCP：把同一批能力包成 MCP server，桌面端换成 MCP client。

## 决策 6：单用户档案，先建档再谈多用户

### 一句话
**这一版就是给 Wen 一个人用的；但表结构里已经留了"用户"的位置，以后加第二个用户不用重写记忆层。**

### 场景

**场景 A（现在）**：只有你一个人用，所有任务、提醒、对话都属于你。名字影响称呼和"这是谁的画像"。

**场景 B（以后）**：你想让家人也用，或者手机上也要有自己的一份。这时需要"每个用户一套数据"。

### 最后怎么做

`user_profile` 存 4 个键（见决策 0）；`semantic_facts` 有 `subject` 字段（当前固定 `'user'`）；`chat_events` 有 `session_id`（当前固定 `'default'`）。

也就是说：
- **现在**：单租户，所有数据一套；
- **结构上**：已经能区分"哪个用户/哪个会话"，只是还没用起来。

### 为什么不上账号体系
- 现在上登录、权限、迁移，收益为零，复杂度提前压到 MVP；
- 但字段先留好，以后加第二个用户只需要：`subject` 从固定值改成变量、`session_id` 按用户生成、窗口加一个切换入口。

### 你会感觉到的差别
- 现在：打开就是你，不用登录；换电脑要手动拷 `data/baymax.db`。
- 现在**没有**：多用户隔离、云同步、权限控制。

### 什么时候该换
- 需要第二个人用 → 先做"用户切换 + 数据隔离"；
- 需要多设备 → 先做 HTTP 服务（决策 5），再谈账号。

## 决策 7：模型"只报喜不落地"——先锁工具，再核对结果，最后丢历史重试

**场景**：连续聊了五六轮后，用户说"明天下午两点提醒我交实验报告"。`glm-4-flash` 回了"已设置提醒"，但 `reminders` 表是空的；又说"答辩稿那项我做完了"，回了"已标记完成"，任务其实还是待办。用户不会去查库，只会以为事情办好了。

这不是提示词没写清楚——规则里已经写了"没有调用就不能说已经办好"。问题在于多轮历史会把模型带偏，`tool_choice` 也不保证被服务端强制执行。

**两种做法**：

1. **继续加提示词、加 fewshot**：零成本，但本质是把规则再说一遍，模型该不调还是不调，无法验证。
2. **在代码里做结果核对**（本轮选择）：先按意图锁定工具，再看回复和真实写操作是否一致，不一致就换干净的上下文重试，仍不行就如实告知。

**具体三层**（`core/brain.py`）：

| 层 | 做什么 | 关键函数 |
|---|---|---|
| 第一层：意图锁定 | 提醒/更新/查询进展等意图明确时，首轮用 `tool_choice={"type":"function","function":{"name":...}}`；建任务不锁，交回模型排 due/domain | `force_tool_for` / `_stream_once` |
| 第二层：结果核对 | 只有本轮确实要求写入时，才检查回复是否含"已设置/已记下/已标记"；同时要求本轮有成功写工具，或规则抽取真的写入了事实 | `claims_done` / `_has_write_success` / `fact_written` |
| 第三层：丢历史重试 | 不一致时，丢掉多轮历史，只保留稳定前缀 + 当前时间/上下文 + 当前这句话，重试最多 2 轮；仍不一致就回"刚才只是嘴上说办好了，实际没写进系统，你再说一次" | `ask_baymax` 4.1 节 |

**为什么不是"直接自己解析参数、绕过模型"**：提醒/任务的自然语言表达太散（"下下周的周五""答辩稿那项"），自己写解析器会引入另一套错误；模型在**单句、无历史**时调工具是可靠的，所以只换上下文，不换执行者。

**代价与边界**：

- 多一次模型调用（仅在不一致时）；写入类回复不再流式输出，等落库后再显示，避免"先报喜后打脸"。
- 重试仍失败时用户会看到如实提示，这是有意为之——宁可承认没办，也不假装办好。
- 查询类回复（"您设置了一个提醒…"）不触发拦截；早期版本曾误伤，已修为"仅本轮要求写入才检查"。
- 建任务强制工具会打乱模型排 due/domain，已回退为不强制。

**验证**：`tests/test_regressions.py` 的 `test_fake_claim_is_caught_and_retried`、`test_fake_claim_without_tool_is_not_believed`；`scripts/chat_flow.py` 11 轮流程第 6 轮真实落库；`scripts/task_eval.py` 19/19。

## 决策 8：外部能力用 stdio MCP 客户端，不把每个服务写进主代码

### 场景
你想让 Andy 查日历、搜本地文件、开浏览器。按第一版的工具注册表，每接一个能力都要改 `core/tools.py`、重启程序；接五个就是五段互不相干的代码，权限也各写各的。

### 两种做法
- **做法 A：全部写成内置工具。** 简单、可控，但核心仓库会越来越胖，第三方服务更新一次就要改一次代码。
- **做法 B：MCP 客户端。** Andy 启动时读配置，连上外部 server，自动发现对方有哪些工具，再转成模型能看懂的 schema。加服务只改配置。

### 决定（2026-11-26）
**用做法 B，先实现 stdio 传输的 MCP 客户端，不引入第三方 `mcp` SDK。** 理由：协议本身不复杂（JSON-RPC 2.0 + 换行分隔），自己写能精确控制超时、权限、错误隔离，也少一层依赖。远程 HTTP/SSE 这一期不做。

### 流程（从启动到调用）
1. `main.py` 调 `mcp_client.start_all()`，读 `mcp_servers.json`；文件不存在就只记一条日志，内置工具照常用。
2. 每个启用的 server 起一个子进程：`command + args`，工作目录 `cwd`，环境变量合并 `env`。
3. 发 `initialize`（协议版本、clientInfo），收到结果后发 `notifications/initialized`。
4. 调 `tools/list`，支持 `nextCursor` 翻页；每个工具取 `name / description / inputSchema / annotations`。
5. 适配成 `mcp__<server>__<tool>`：名字只留字母数字下划线横线，避免和内置工具重名；描述加 `[MCP:server]` 前缀。
6. 模型选中后，`tools.call_tool()` 按前缀路由；`MCPManager` 先过权限门，再发 `tools/call`。
7. 返回 `content` 里的文本或 `structuredContent`；`isError=true` 收敛成 `{"ok": false, "error": ...}`，不打断整轮对话。

### 函数卡片
| 函数 | 归属 | 参数 | 返回 | 用错后果 |
|---|---|---|---|---|
| `load_servers(path)` | `mcp_client` | 配置文件路径 | `{name: ServerConfig}` | 不校验 `command` → 启动时才炸；相对 `cwd` 不按配置文件目录解析 → 找不到脚本 |
| `MCPClient.start()` | 单个 server | 无 | 无（失败抛异常） | 不设超时 → 一个坏 server 卡住整个启动 |
| `MCPClient._request(method, params, timeout)` | 单个 server | 方法、参数、超时 | `result` 字典 | 并发写同一 stdin 不加锁 → 响应串包；不按 id 匹配 → 拿错结果 |
| `MCPClient.list_tools()` | 单个 server | 无 | 原始工具列表 | 不处理 `nextCursor` → 只拿到第一页 |
| `MCPClient.call_tool(name, args)` | 单个 server | 原始工具名、参数 | `{ok, content/error}` | 把 `isError` 当成功 → 模型以为办成了 |
| `MCPManager._adapt_tool(server, cfg, raw)` | 管理器 | server 名、配置、原始工具 | 无（写入 `tools`/`_by_name`） | 不设上限 → 工具 schema 撑爆上下文；不判 `readOnlyHint` → 写入工具被当只读放行 |
| `MCPManager.call_tool(fn_name, args)` | 管理器 | 带前缀的函数名、参数 | 工具结果 | 不查权限 → 外部工具直接改你的文件/日程 |
| `tools.get_tools()` | 工具层 | 无 | 内置 + MCP schema | 只返回内置 → 模型永远看不到 MCP 工具 |

### 权限与隔离
- **只读**：`annotations.readOnlyHint=true` 直接放行；server 配置 `assume_read_only=true` 可把整台 server 当只读。
- **写入**：必须同时满足全局 `MCP_ALLOW_WRITE=1` 和 server 配置 `allow_write=true`，并且有确认回调；终端是 y/N，窗口是主线程 Qt 对话框（后台线程通过信号回主线程，不能直接开 `QMessageBox`）。
- **无回调**：默认拒绝，不猜用户意图。
- **失败隔离**：某个 server 启动失败、超时、进程退出，只进 `errors` 并跳过；`health_check` 报 FAIL，但内置任务/提醒/记忆不受影响。
- **注入风险**：工具描述和返回内容都来自外部 server，默认不完全可信；不把返回文本当系统指令执行，写入必须确认。

### 代价与边界
- 只支持 stdio；远程 HTTP/SSE、OAuth、断线重连、自动拉起都还没做。
- 一个 server 一个进程；server 挂了不会自动重启，要等下次启动。
- 工具最多暴露 `MCP_MAX_TOOLS=24` 个，单次请求超时 `MCP_TIMEOUT=20s`；工具太多会挤占上下文。
- `mcp_servers.json` 可能含本机路径/密钥，已加入 `.gitignore`；仓库只留 `mcp_servers.example.json`。

**验证**：`tests/test_mcp.py` 7/7（握手、发现、只读、写入拒绝、写入确认、坏命令隔离、无配置）；本地 demo server 真实跑通 `tools.get_tools()` 暴露 11 个工具、`call_tool()` 路由 echo 和 write_note。

## 决策 9：语音用 edge-tts 在线合成，Windows SAPI 兜底，语种与音色分开设置

### 场景
你希望 Andy 把回复读出来，最好音色自然；但网络断了、或者 edge 接口抽风时，不能连文字对话一起卡住。

### 两种做法
- **做法 A：只接一个云端 TTS。** 音色最好，但断网就哑，且每次都要等网络。
- **做法 B：在线为主 + 本地兜底。** 正常走 edge-tts；失败自动切 Windows SAPI；都失败就只显示文字。

### 决定（2026-11-26 初版，2026-11-27 修订为“语种与音色分离”）
**用做法 B。** 默认关闭，窗口勾选“语音”或 `.env` 设 `TTS_ENABLED=1` 才播；不默认打扰。

语种和音色拆成两套独立设置，不再用一个档位同时承担两件事：

- `language_mode`（回复语种）：`auto`、`zh-CN`、`zh-TW`、`en-US`、`en-GB`、`en-CA`、`en-HK`，默认 `auto`。它只决定模型用哪种语言回答。
- `voice_mode`（朗读音色）：`follow`、`zh-CN`、`zh-TW`、`en-US`、`en-GB`、`en-CA`、`en-HK`、`sapi`，默认 `follow`。它只决定 `edge-tts` 用哪个声音。
- `follow` 表示“跟着回复语种走”：中文用大陆中文音色、繁體用台灣音色、英文按所选地区选对应英文音色；`auto` 语种下再按文本中英文判断。
- 手动指定音色后，即使和回复语种不一致也允许保存。界面用 `mismatch_warning()` 提示“跨语言朗读可能不自然”，但不拦截；音质是否可用由用户试听决定。
- 旧设置自动迁移：旧 `voice_mode=zh/en/auto/offline` 转成“对应语言 + follow/sapi”；旧语种和音色同名的绑定档转成“同语种 + follow”。

| 回复语种 `language_mode` | 回复语言 |
|---|---|
| `auto` | 跟随提问语言 |
| `zh-CN` | 简体中文 |
| `zh-TW` | 繁體中文（台灣用語） |
| `en-US` | 美式英语 |
| `en-GB` | 英式英语 |
| `en-CA` | 加拿大英语 |
| `en-HK` | 清晰英文，香港语境 |

| 朗读音色 `voice_mode` | 实际音色 |
|---|---|
| `follow` | 按当前回复语种自动选：`zh-CN-YunxiNeural` / `zh-TW-HsiaoChenNeural` / `en-US-BrianMultilingualNeural` / `en-GB-RyanNeural` / `en-CA-LiamNeural` / `en-HK-SamNeural` |
| `zh-CN` | `zh-CN-YunxiNeural` |
| `zh-TW` | `zh-TW-HsiaoChenNeural` |
| `en-US` | `en-US-BrianMultilingualNeural` |
| `en-GB` | `en-GB-RyanNeural` |
| `en-CA` | `en-CA-LiamNeural` |
| `en-HK` | `en-HK-SamNeural` |
| `sapi` | Windows SAPI 系统语音 |

### 为什么拆开
初版把语种和音色绑成八档，选 `en-GB` 就同时切“英式英语回复 + `en-GB-RyanNeural` 朗读”。这适合“口音和语言一起换”的场景，但用户可能只想换回复语言、保留熟悉的中文音色，或者只想试另一个英文嗓子而不改回复语言。绑定档位无法表达这些组合，所以拆成两个独立键。

代价是允许出现跨语言组合：按地区/locale 设计的音色（`en-GB-RyanNeural`、`en-CA-LiamNeural`、`en-HK-SamNeural`、`zh-CN-YunxiNeural`、`zh-TW-HsiaoChenNeural`）念另一种语言时通常不自然，部分组合可能合成失败。`en-US-BrianMultilingualNeural` 是多语音色，跨语言相对更稳。因此设计成“提示但不阻止”，把最终判断交给用户试听，而不是替用户禁掉组合。

### 流程
1. `speak(text)` 先判开关；关闭直接返回 False。
2. `clean_tts_text()` 去代码块、行内代码、Markdown 链接、URL、HTML 标签、符号、emoji，压缩空白，超过 `TTS_MAX_CHARS=240` 按句号截断。
3. 新消息打断上一段：`stop(clear=True)` 停 pygame、清队列；工作线程取到新文本后清中断标记。
4. `pick_profile()` 定音色：显式 `voice_mode` 对应的音色优先；`follow` 时按当前 `language_mode` 选对应地区音色，`auto` 再按文本中英文判断；`sapi` 不选在线音色。
4.1 `set_language_mode(mode)` 只改回复语种状态，并同步给模型 `LANGUAGE_INSTRUCTIONS` 约束；它不再改 `TTS_VOICE`、`TTS_RATE`、`TTS_PITCH`。`set_voice_mode(mode)` 只改音色状态与 `TTS_VOICE/TTS_RATE/TTS_PITCH`，`follow` 清空显式音色，`sapi` 设 `speaker.prefer_offline=True`。旧设置档位在 `BaymaxWindow.__init__` 里迁移成这两个键，避免直接覆盖用户配置。
5. **2026-11-28 调整**：GUI 不再在流式阶段分句朗读；`_on_done()` 拿到完整 `reply` 后只调用一次 `speak(reply)`。`split_tts_text()` / `StreamFeed` 仍保留在模块和测试里，作为旧接口/兼容能力，但窗口不再使用。
6. `_play_edge()` 对整段文本只生成一个音频文件，再查缓存（`logs/tts/<sha1>.mp3`，key 含 voice/rate/pitch/volume/text），没有就 `edge_tts.Communicate(..., pitch=...)` 合成；失败重试 1 次，再退回 SAPI。
7. `_play_file()` 用 pygame 播放，轮询 `get_busy()`，被中断就 `music.stop()`；启动时 `warmup()` 预热音频设备。
8. edge 失败 → `_play_sapi()`：pyttsx3 新建 engine，按 lang 选中文或英文系统声音，`runAndWait()`；失败只警告一次。
9. `shutdown()` 停线程、清队列、退出 mixer。

### 函数卡片
| 函数 | 归属 | 参数 | 返回 | 用错后果 |
|---|---|---|---|---|
| `clean_tts_text(text)` | `voice` | 原始回复 | 可朗读文本 | 不清洗 → 把代码、URL、Markdown 符号全念出来 |
| `Speaker.speak(text, interrupt=True)` | 单例 `speaker` | 文本、是否打断 | bool | 阻塞调用 → 窗口卡住；不清队列 → 旧回复排队念 |
| `pick_profile(text)` | `voice` | 文本 | `{voice,rate,pitch,lang}` | 不按语言选 → 中文用英文音色；忽略显式音色 → 用户选了嗓子又被覆盖 |
| `split_tts_text(text, max_len)` | `voice` | 文本、段长 | 句子列表 | 旧接口，GUI 不再调用；保留给兼容/测试，误接回窗口会恢复逐句起播 |
| `StreamFeed.feed(delta)` | `voice` | 流式增量 | 完整句子列表 | 旧接口，GUI 不再调用；误接回窗口会恢复流式朗读 |
| `Speaker._play_edge(text)` | 内部 | 文本 | bool | 不设超时 → 网络挂起时 worker 卡死 |
| `Speaker._play_file(path)` | 内部 | mp3 路径 | bool | 不轮询中断 → 用户发新消息后还在念旧内容 |
| `Speaker._play_sapi(text, lang)` | 内部 | 文本、语言 | bool | 不按 lang 选 → 英文文本用中文声音念 |
| `set_language_mode(mode)` | `voice` | auto/zh-CN/zh-TW/en-US/en-GB/en-CA/en-HK（兼容 zh/en/offline） | 实际语种 | 把它当音色设置用 → 语种换了但嗓子没换，或反过来 |
| `set_voice_mode(mode)` | `voice` | follow/zh-CN/zh-TW/en-US/en-GB/en-CA/en-HK/sapi | 实际音色 | 只改语言不改它 → 音色仍停在旧嗓子；`sapi` 不清显式音色 → 在线音色仍被尝试 |
| `current_language_mode()` / `current_language()` | `voice` | 无 | 语种档位 / `zh`、`en` 或空 | 用 `TTS_VOICE` 反推语种 → 显式音色会误导判断 |
| `current_voice_mode()` | `voice` | 无 | `follow/sapi/地区档` | 把它当语种读 → 跨语言组合被误判 |
| `mismatch_warning(language, voice)` | `voice` | 语种、音色 | 提示文本或空串 | 不提示 → 用户选到不自然组合却不知道 |
| `language_instruction(mode)` | `prompts` | 语种档位 | 语言约束文本 | 不注入 → 模型跟着历史中文回答 |
| `language_choices()` / `voice_choices()` | `voice` | 无 | `[(key, label)]` | UI 写死档位 → 新语种/音色选不到 |
| `health_check()` | `voice` | 无 | bool | 只看 import 不看设备 → 有库但没声卡时仍报 OK（播放时会降级） |

### 代价与边界
- edge-tts 需要网络，整段合成耗时随文本长度增加；同一段有缓存，重复不再请求。
- 六套在线音色都真实存在于 edge-tts。语种与音色已解绑，允许跨语言组合，但不保证音质：按地区设计的音色念另一种语言通常不自然，部分组合可能合成失败；`en-US-BrianMultilingualNeural` 是多语音色，跨语言相对更稳。界面只提示，不替用户禁用组合。
- 英文语种只控制拼写/用词，地区口音由对应音色体现；模型不保证 100% 不混入美式拼写，必要时后续加拼写后处理。
- SAPI 音色比 edge 机械，语速/音量可调但情感有限；离线模式只能选系统已安装的声音，且不强制回复语种。
- 整段合成意味着长回复要等文字全部生成完才出声；`TTS_MAX_CHARS=240` 仍会截断超长内容，没有词级同步高亮。
- 播放依赖 pygame/SDL 音频设备；设备不可用时只显示文字，不反复重试。
- 长回复截断到 240 字，避免念完整篇报告；需要完整朗读可调大 `TTS_MAX_CHARS`。

**验证**：`tests/test_voice.py` 15/15（清洗、截断、音色路由、语种与音色独立、旧值迁移、跨语种提示、`follow` 跟随、整段一次合成、队列、降级、健康检查）；6 个选定音色真实合成成功（`logs/voice_check/`）；整段中文回复真实合成 1 个 mp3（5.376 秒，`logs/tts_whole_reply_check.mp3`）；真实模型 `brain.ask_baymax("你是谁？")` 在 `en-GB/en-HK/en-US/en-CA` 下均返回英文，在 `zh-TW` 下返回繁體中文，`zh-CN/auto` 保持中文。解绑后 `set_language_mode("en-GB")` + `set_voice_mode("zh-CN")` 仍保持英文回复、音色为 `zh-CN-YunxiNeural`，两项互不覆盖。

## 决策 9.1：语音输入选 Vosk 离线小模型，不接云端识别（2026-11-28）

### 场景
Wen 想不敲键盘，直接说“明天下午三点提醒我交周报”，文字进输入框后再确认发送。要求录音不出本机、安装不复杂、在 PyQt6 窗口里不卡 UI；不要为了一个语音输入引入 torch、CUDA 或几个 GB 的依赖。

### 两种做法
- **做法 A：在线识别 API（Google/Whisper API 等）。** 识别准、模型不占硬盘，但录音要上传，网络不稳就不可用，还要处理密钥与费用。
- **做法 B：本地 Vosk 中文小模型 + `sounddevice`。** 约 42MB，CPU 可跑，不需要 torch；识别在本地完成。准确率不如大模型，嘈杂环境更明显。

### 决定
**用做法 B。** 先保证“离线、能装、能跑”，不把识别准确率押在云端；模型外置到 `models/`，不塞进仓库和 exe。

### 流程
1. `core/asr.py` 懒加载 `vosk.Model`；`model_available()` 只检查目录和 `am/`，不阻塞启动。
2. `record_until(stop_event)` 用 `sd.RawInputStream` 采 16kHz / 单声道 / int16，`AcceptWaveform` 拿分段结果，`PartialResult` 回填临时文本，`FinalResult` 收尾。
3. `normalize_text()` 去掉汉字之间的空格，保留英文单词间空格；多段停顿用逗号连接。
4. `ASRWorker(QThread)` 把加载、录音、识别放到子线程，通过 `partial/done/error/state` 回主线程；按钮点一下开始、再点一下停止，结果只填输入框，不自动发送。
5. `send()` 时若还在录音，先停并丢弃迟到的 ASR 结果，避免把文字又写回输入框；`closeEvent()` 停线程并等待退出。

### 代价与边界
- 小模型对安静环境短句够用；口音、嘈杂环境、长句准确率会下降，标点不保证。
- 首次加载模型有几百毫秒到数秒开销；模型缺失/依赖缺失/麦克风打不开时给可读提示，键盘输入不受影响。
- 没有唤醒词、没有流式云端识别、没有说话人分离；真人麦克风端到端仍需复测。

**验证**：`tests/test_asr.py` 7/7；真实模型 `vosk-model-small-cn-0.22` 完整下载 43,898,754 字节，识别中文 TTS 样本输出“你好我是安迪”；`sounddevice` 识别到本机麦克风阵列，16kHz/单声道/int16 参数校验通过。

## 决策 10：日期/星期/时间本地确定性回答，不交给模型

### 场景
Andy 在窗口里回答“现在是 2026年11月27日 星期日 14:02”：日期对，星期和时间都错；用户追问“时间错了吧”，它仍重复同一句。系统实际时间是 `2026-11-27 19:49 星期五`。动态时间文本本身注入正确，是模型忽略/幻觉了星期和时间。

### 两种做法
- **做法 A：继续靠 prompt 约束。** 成本最低，但模型仍可能不看注入的时间，同类错误会复发。
- **做法 B：基本问答走本地时钟，模型回复再做一次校准。** 日期/星期/几点这类“查表就能答”的问题不调模型；通用回复里出现“今天/完整日期 + 星期/时间”时，用 `datetime.now()` 纠正。

### 决定（2026-11-27）
**用做法 B。** 在 `ask_baymax()` 入口、模型调用之前拦截短句问法；模型回复落地前再跑 `calibrate_reply_time()`。条件句（“如果今天是星期日”）不改，避免把假设改成事实。

### 流程
1. `answer_basic_query(text)` 先做标点/空白归一化；超过 16 字或含“提醒/明天/下周”等任务词直接放行。
2. 命中“今天星期几 / 今天是几号 / 现在是几点”等固定问法时，用本机 `datetime.now()` 生成答案，记一条 user/assistant 事件后直接返回，不调用模型。
3. 未命中的正常对话走模型；回复返回后 `calibrate_reply_time()` 检查“现在是/今天是 + 完整日期 + 星期 [+ 时间]”。
4. 日期可解析时按该日期重算星期；如果日期就是今天，时间也换成当前 `HH:MM`；非今日日期只校星期、保留原时间。
5. 匹配位置前 6 个字含“如果/假如/假设/要是/若/不是/并非/除非”时跳过，避免改坏条件句。
6. 校准发生时写一条 `[brain] 校准时间表述` 日志，便于复盘模型又乱答。

### 函数卡片
| 函数 | 归属 | 参数 | 返回 | 用错后果 |
|---|---|---|---|---|
| `answer_basic_query(text, now=None)` | `brain` | 用户原话、可选时间 | 本地答案或 `None` | 拦截过宽 → 把“明天提醒我”当时间问答；过窄 → 模型继续瞎猜 |
| `calibrate_reply_time(reply, now=None)` | `brain` | 模型回复、可选时间 | 校准后的回复 | 不设条件句保护 → 把“如果今天是星期日”改成星期五 |
| `current_time_text()` | `brain` | 无 | 注入 prompt 的时间文本 | 只注入不校验 → 模型仍可能忽略它 |

### 代价与边界
- 只覆盖短句、明确问法；“下周五几点”“三天后星期几”仍交给模型/后续日期解析器。
- 依赖本机系统时区与时钟；系统时间本身错了，回答也会错。
- 校准只处理“完整日期 + 星期”这种强格式，不猜模糊表达。
- 拦截会跳过模型，因此这类问题不会有模型的额外解释或延伸建议。

**验证**：`tests/test_basic_answers.py` 8/8；`ask_baymax` 实跑 `今天星期几`、`现在是几点`、`今天是几号` 均返回本机时间，且不触发模型调用。

## 附录 D：已知边界（还没做和做不精确的地方）

按"影响大小"排序，都是如实记录，不是藏起来的坑。

| # | 边界 | 具体表现 | 影响 | 改法 / 状态 |
|---|---|---|---|---|
| 1 | 程序关闭时提醒不响 | 依赖进程内心跳 | 关机/退出期间错过 | Windows 计划任务开机自启 |
| 2 | ~~迟到 ≤10 分钟静默跳过~~ | 已改为启动时标"刚到点"并补发 | — | **已解决**（`_catch_up`） |
| 3 | ~~换说法召回不到~~ | 已上 embedding + RRF；"那个证的事"实测 0.11 排第一 | — | **已解决** |
| 4 | 语义检索仍可能带噪声 | 已加语义门槛 + 近义去重 + 主题加权，top3 噪声 0.70→0.10；但仍是启发式，换个领域可能失手 | 上下文变长、模型被误导 | 扩语料复测；上千条后再上 rerank |
| 5 | 阈值是"本地标定值" | 0.10 来自 8~16 条小语料，0.80 门槛来自 10 问句评测 | 语料变大后可能偏松/偏紧 | 用 `memory_eval.py` 加自己的问句复核 |
| 6 | 向量补索引有延迟 | 后台线程按旧→新补，旧事件可能暂时只有关键词 | 新装/换模型初期召回偏弱 | 运行 `backfill_embeddings.py` 手动补完 |
| 7 | 向量缓存占内存 | 最近 1000 条 ×2048 float32 ≈ 8MB，另存中心化副本 | 内存多约 16MB | 上限可调；几千条后考虑分片 |
| 8 | 规则抽取仍会漏长尾表达 | 已修“过敏原取关键词前主体”“问句不写事实”“记一下/是不是前缀剥离”，但“我下周有考试，但还没复习”这类复合句仍可能抽歪 | 生僻说法记不住 | 改规则取短语，或异步模型抽取 |
| 9 | 已完成任务不能按标题改 | `find_by_title` 只查未完成 | "把那个再改回未完成"要先查编号 | 允许 `include_done`，或界面直接改 |
| 10 | 画像不能删除 | 没有 UI 入口 | 记错的事实会一直注入 | 加"画像"页 |
| 11 | 工具循环最多 4 轮 | 防死循环 | 超复杂任务可能被截断 | 调大上限 + 单轮超时 |
| 12 | 多用户/多设备不支持 | 单租户、本地库 | 换电脑要拷库 | HTTP + 账号 |
| 13 | token 是估算 | 中英混合不精确 | 预算判断有偏差 | 接 tokenizer 精确计数 |
| 14 | 对话与向量都依赖网络 | 对话走智谱；向量走 embedding 接口 | 断网不能聊；向量挂了自动退回关键词，本地功能仍可用 | 本地小模型兜底（成本高，暂不做） |
| 15 | MCP 只支持 stdio | 没有 HTTP/SSE 传输、OAuth、断线重连 | 只能接本机 server；远程服务要另做传输层 | 后续加 HTTP/SSE + 超时重连 |
| 16 | MCP 写入默认全关 | 全局 `MCP_ALLOW_WRITE=0`，server 还要 `allow_write=true` | 忘了开就一直拒绝，不会误写 | 按需开；每次仍会确认 |
| 17 | MCP 工具描述不完全可信 | 描述和返回来自外部 server | 恶意 server 可能诱导模型调用危险工具 | 只接可信 server；写工具逐次确认；不把返回当指令 |
| 18 | 语音依赖网络与音频设备 | edge-tts 需联网；SAPI 需声卡 | 断网首句慢；无设备时静音 | 失败只提示一次，不阻塞文字；可调 SAPI 兜底 |
| 19 | 语音输入先做 Vosk 离线小模型 | 没有唤醒词、没有说话人分离、真人麦克风端到端未复测 | 不联网也能说；准确率受环境影响 | 后续按实际识别质量决定换大模型或加云端口径 |
